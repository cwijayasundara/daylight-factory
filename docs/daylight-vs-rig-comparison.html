Daylight vs Rig: Deep Architecture Comparison

A side-by-side technical analysis of two Claude Code SDLC harnesses built around the Anthropic AI-Native SDLC Playbook — comparing an autonomous lights-on software factory (Daylight) against a human-in-the-loop team governance harness (Rig).

Daylight: eigen_work_v2.0 (main) Rig: rig_v1 Runtime: Node.js + TypeScript (zero build) Reference: Anthropic AI-Native SDLC Playbook

1. Executive Summary: Two Complementary Poles

The Core Insight: Daylight and Rig are not duplicates — they solve different operating models. Daylight optimizes for autonomous throughput (hand a PRD to a headless orchestrator and get a reviewed, deployed, smoke-tested service with 0 or 2 human touchpoints). Rig optimizes for team engineering discipline & governance (interactive Claude Code sessions where humans always approve, contracts freeze on approval, mutation-diff + hidden holdout tests block regressions, and CI + branch protection enforce the boundary across 8 language stacks).

Red-proof + Mutation-diff + Hidden Holdouts: red-proof against base, blocking mutation score (default 80% on added lines), and QA black-box holdout tests hidden from the builder by hooks.

Production gate template (managed hook) + CI rig-check / merge_group. Does not orchestrate Docker compose deploy/smoke inside the inner loop.

Continuous/commit/CI/nightly cadenced sensors (model-grade aware), knownRed debt baseline for brownfield, test-tamper/weakening detection, size caps, secret scanning.
Code & Security Review Narrow Opus evaluator (inline rubric) per [test] task + Run Judge + /code-review & /security-review (with local-diff fallback when origin/HEAD is absent) + cited blocking rule. One clean-context Opus reviewer + Opus security agent per change, plus CI ai-review. Review-health audit seeding (sdlc audit seed|reveal) & Q1/Q2/Q3 reviewer comprehension checks.
Security & Guardrails PreToolUse guard hooks block credential reads, pushes to default branch, foreign deploys, and generator edits to protected files/rubrics. Removed brittle Bash hooks in v0.5.0; uses Claude permissions deny/ask rules locally and treats CI + GitHub branch protection (reading base-branch checker/config) as the real trust boundary.

Observability & Cost Control Append-only hash-chained JSONL audit log (every tool, REPL batch, subagent, sensor, verdict, review cost) + self-contained HTML report. Live journey dashboard (context & dollars), 150k context compact guard, Opus advisor disabled, verify.json stamp caching, sdlc report --github (merges/reverts per tier).

Distribution & State Claude Code plugin (.claude-plugin/) + CLI; runtime state in gitignored .daylight/. Standalone vendoring (vendor --standalone) commits skills/agents/hooks/bin into the repo; change evidence committed under .rig/.

5. Strategic Recommendation: How to Use Both

Use Daylight When

Hands-Off Autonomous Delivery

  • You want a 0-gate or 2-gate factory that takes a PRD/issue and delivers a deployed, smoke-tested service.
  • You are running scheduled jobs, alert-driven bug fixes, or rapid greenfield TypeScript services.
  • You want a single hash-chained audit trail and HTML report per run.
Use Rig When

Team Daily Driver (Polyglot)

  • Your engineering team works interactively in Claude Code across Java, Python, Go, Rust, .NET, Angular, or Node.
  • You need strict enterprise CI governance (human-only approvals, branch protection, mutation-diff, hidden holdouts, revert breaker).
  • You have large brownfield repos with legacy debt (knownRed).
Best-of-Both Convergence

Steal From Each Other

  • Port from Rig → Daylight: knownRed brownfield baseline, multi-stack packs, mutation-diff sensor, and CI-enforced base-branch boundary.
  • Port from Daylight → Rig: Pre-merge Docker verifyDelivery ([run] ACs), headless worktree orchestrator for rung-3 unattended batches, and hash-chained HTML run reports.
